# 财税 Agent 产品版设计说明

本文说明产品版当前实现，对齐初赛材料包 v1.1.0。官方评审关注作品完整度（45%）、问题理解与方案契合度（20%）、后续完善空间（10%）和创新性（25%）；赛题二侧重任务记忆、规则文档、上下文管理、工具执行、过程可检查和自然表达，并要求合理划分模型、规则和程序工具的职责。真实模型复验使用与官方评测相同的模型 ID `qwen3.8-max`（OpenAI 兼容接口），不能据此宣称已经过官方评测环境或统一 Key 验收。下文只陈述能在 `product/` 源码中核实的事实。

## 1. 已完成和未完成的功能

**已完成（三个场景共用同一套对话与工具流程）：** 按当前企业与会计期间查询发票总额、银行收入和银行支出，并引用适用规则；只允许按用户原文补充发票用途或备注，经建议卡确认后保存并回查；多轮检查可追问、更正、取消，并保留每账号每企业至多一个未完成任务。金额由程序按整数分汇总并渲染；查看者不能写入；无授权企业不可见。工作台为 Next.js + Nginx HTTPS、Spring Boot、PostgreSQL（含 pgvector）、Redis、Celery、SeaweedFS、FastAPI + LangGraph。

**未完成或只部分完成：** 程序自动收尾（R5）未实现；团队自写的 B01—B35 尚未在 v1.1.0 数据上全量复验（已完成的是合成数据上 B24/B34 三轮 18/18 及 P6 持久化 4/4，以及导入后的权限、规则、门槛和一次月度查询）；发票只有会计期间、没有按日开票日期；不执行真实记账、付款或申报，也不做发票识图。启动脚本默认会为租户 `contest` 补齐捆绑的官方样例数据，详见第 5 节与 `product/数据导入说明.md`。

## 2. 模型、规则与程序的职责划分

模型负责理解用户需求，并在每轮最多六次决策中选择 `tool`、`ask`、`answer` 或 `propose`：是否追问、调用哪一个工具、是否生成补全建议。模型不能自行确认保存，也不能通过工具参数改写企业、月份或身份。偏好只影响表达与默认值，不能改变权限或确认流程。

程序负责确定性计算、校验和落库：金额以整数分存储，由 `guards.render` 按本轮成功工具证据渲染；Java 用会话 Cookie 与企业授权表检查角色；`Invoices.validateChanges` 只接受 `purpose` 和 `note`；确认须用户点击，写入后回查；规则按发布状态、生效月份和金额门槛选择，退役版本不作当前依据。

程序里的 `required_by_text` 和 `proposal_claim` 是校验与提示，不是用关键词匹配替代模型理解：前者可预登记需求种类，模型仍可在首次决策中补充合法需求，此后由程序固定；后者只拦截没有真实提案事件的完成声明。没有本轮成功工具证据时，程序不会宣布业务成功。

## 3. 记忆、规则、上下文与数据操作

任务、消息、轨迹、偏好和操作由 Java 写入 PostgreSQL，Agent 不直连数据库，每轮通过 `context` 领取上下文。登录会话在 Redis。任务进度、长期偏好、规则检索和当前企业上下文分开存放：每企业一个未完成任务由部分唯一索引保证；偏好可新建、更正、删除并写审计，更正后旧来源退出上下文；规则经独立检索进入本轮证据，不冒充记忆。历史最多八条，另含最近五条操作摘要；保存事实仍须本轮 `get_operation` 证据。记忆按账号、租户和企业隔离。

规则表保存版本、生效月份和状态（`draft` / `published` / `retired`）。实时检索与核验只使用已发布且覆盖当前期间的规则，再按字面命中和 pgvector 排序。说明类规则（R001、R004）可检索，但因 `required_fields` 为空不参与选规。甲企业 2026-09 使用已发布的 R002 2.0（每张必填用途）；已停用的 R002 1.0 可在版本列表中查看，但不出现在 9 月检索中。乙企业 R003 1.0 通过 V9 列 `min_amount_cents` 落实「大于或等于 1000.00 元须填用途」（含等于，未知金额偏保守）。确认保存时若适用规则已变化则退回。

上下文预算由 `PRODUCT_CONTEXT_BUDGET` 控制（推荐 24000 字节；未填写时代码缺省 12000，官方月度查询会超限）。超限先裁历史再裁偏好，仍超则 `context_budget_exceeded`，待办保留。业务数据必须本轮重新查询。

保存路径为「提案 → 用户确认 → 事务写入 → 回查」。服务端锁定发票，校验权限、`revision` 和规则后更新用途或备注，`revision` 加 1，并以回查为准。`Idempotency-Key` 重复确认返回同一回执。失败说明原因，不误报成功。

运行记录见工作台右侧「过程与依据」：需求、步骤、工具、证据、拦截和上下文预算；「查看完整轨迹」展开已脱敏的模型输入。轨迹写入 `agent_trace`，不记录密钥。

## 4. 创新点与评审关注点对应

下表对应评审给出的优化方向。证据中的 18/18 指隔离实例上 `qwen3.8-max`、提交 `72f6899` 的三轮复验，数据为合成种子，不是 v1.1.0 全量 B 用例。

| 方向 | 产品做法 | 代码位置 | 可核对证据 |
| --- | --- | --- | --- |
| (a) 从「简单调用工具」到规划、执行和结果核对 | 同一 LangGraph 循环中登记并固定需求，模型选择工具或追问；工具由 Java 执行；最终答案必须用 `answer_items` 引用本轮证据，金额和规则由程序渲染 | `agent/executor.py`，`agent/guards.py`（`render`），`AgentChat.java` | `test_program_registration_and_hints`；`verify_agent.py`；`verify_external.py` 中 B24-01；`verify_contest.py --chat` |
| (b) 从「只记住对话」到区分任务、长期记忆、规则和企业上下文 | 任务进度、偏好、规则和当前企业/月份分开组装；偏好可更正删除；历史最多八条，先裁历史再裁偏好 | `AgentTasks.java`（`context`，`agent_task_one_active`），`AgentMemories.java`，`agent/context.py`，`Rules.java` | `verify_memory.py`（含重启后恢复）；运行记录 `P6-B32-restart.json` |
| (c) 从「能查询」到可验证的保存、异常处理和防重复 | 用户确认后锁定发票、校验版本与规则、写入并回查；同键重放返回同一回执；无写权限拒绝；不实「已保存/已生成」被拦截 | `Invoices.java`（`confirm`，`validateChanges`），`AgentOperations.java`，`guards.proposal_claim` | `verify_external.py` 中确认、回查、`revision+1` 与同键重放（B24-04/B34-A）；`verify_contest.py` 中 u002 访问乙企业或修改甲企业被拒绝 |
| (d) 从「单一场景脚本」到统一流程覆盖多场景 | 查询资料、补充保存、多轮检查走同一套对话循环和工具集，不以场景写死分支 | `agent/executor.py` 的 `stream`，`agent/tools.py` | 演示脚本三条主路径；`verify_external.py` 同时覆盖 B24 与 B34 |
| (e) 从「机械回复」到自然、准确地反馈任务状态 | 按证据渲染答案；缺信息用 `ask`；面板区分已回答、需补充和拦截原因；禁止把汇总完成说成已经保存 | `guards.safe_reply` / `proposal_claim`，`web/app/process-panel.tsx`，`executor.py` 的 ask/answer 事件 | `test_finished_summary_is_not_claim`；`verify_ui.py`；修复后的 `round3-B24-01.json` |
| 职责划分 | 模型做理解与决策；程序做计算、权限、白名单、确认、选规和门槛；规则正文与版本由知识库提供，不靠模型默记 | 第 2 节；`Rules.selection` / `requiredFor`，`model_adapter.decision_schema` | `RulesSelectionTest`（含 `amountThresholdIsInclusive`）；`test_tool_enum_and_specific_argument_schema` |

**四项可核对的设计选择：**

1. **提案声明必须对照本轮真实网关事件。** `claims_proposal` 和写操作类措辞须与带 `proposal_id`、`operation_id` 的 `proposal` 事件交叉校验；历史回执不能证明本轮新提案。这避免模型用自然语言冒充「建议已生成」。见 `guards.proposal_claim`，测试 `test_claims_without_gateway_event`、`test_finished_summary_is_not_claim`（「已完成本月汇总」不拦截）。该误报修复后，上述 18/18 复验不再出现此失败。
2. **按动作种类拆分 Schema，工具枚举不含 `ask`。** `ask` 是独立 `kind`；`propose` 的 `changes` 只允许用途和备注；需求登记后 Schema 去掉改写入口。见 `model_adapter.decision_schema`，测试 `test_tool_enum_and_specific_argument_schema`。
3. **乐观并发、保存回查与防重复。** 发票 `revision` 在确认时校验并加 1，写入后读回必须与提案一致；`Idempotency-Key` 保证重复确认不二次修改。见 `Invoices.confirm`，以及 `verify_external.py` 对回查和同键重放的断言。
4. **按生效区间选择规则，并程序化金额门槛。** 已停用的 R002 1.0 保留但不作为 2026-09 依据；R003 用 `min_amount_cents`（100000 分，含等于）决定乙企业哪些发票必须填用途。见 `Rules.java`、`V9__rule_amount_threshold.sql`，`RulesSelectionTest.amountThresholdIsInclusive`，`verify_contest.py` 中的版本检索与缺用途清单。另：真实模型复验每轮从同一 dump 重置并核对状态哈希与 Agent 源码哈希（`verify_external.py` 的 `reset_round`），过程面板使工具、证据和拦截可检查（`verify_ui.py`）。

## 5. 数据导入（简要）

官方样例导入独立租户 `contest`，不覆盖 alpha/beta 合成数据。登录名为小写 `u001`（两家企业可查看并修改）和 `u002`（只能查看甲企业；读乙企业失败，改甲企业失败）。`start.ps1` / `start.sh` 默认在 importer 容器内核对并只补缺失行（`-SkipContestImport` 可跳过），不会覆盖已改过的用途和备注。主工作台 `https://localhost:3443/` 与隔离实例 `tax-product-p8`（`https://localhost:13451/`）均已按此核对。若对 P8 实例从初始 dump 恢复，该实例的 contest 数据需重新导入。查询与保存以数据库当前值为准。完整命令、金额表和限制见 `product/数据导入说明.md`。

## 6. 后续完善空间

对应 10% 的完善空间，下列为已定位、可继续做的事项，不把未做写成已完成：

- **补全官方数据上的场景复验。** 在已导入的 v1.1.0 数据上运行全量 B01—B35（需补齐 `verify_bcases.py`），与合成数据上的 B24/B34 18/18 分开登记。
- **受约束的程序收尾（R5）。** 仅在本轮证据已齐、模型未给出完整 `answer_items` 时由程序渲染金额和引用，并单独统计，避免把它和现有 `guards.render` 混为一谈。
- **按日资料。** 为发票增加开票日期列，以支持按日展示和筛选；当前只有会计期间。
- **延迟与上下文。** 修复前真实模型整轮耗时中位数约 85 秒，需继续观察超时和推理内容，并固定 24000 的输入预算；过程面板补全新工具的中文名称。上述优化也是复赛长对话和规则变化验收的基础。
