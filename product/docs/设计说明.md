# 财税 Agent 产品版设计说明

本文说明产品版当前实现，对齐初赛材料包 v1.1.0 对设计说明的要求：写清已完成与未完成功能、模型与程序分工、记忆与知识管理，以及一个可核对的设计选择。下文只陈述能在 `product/` 源码中核实的事实。

## 1. 已完成和未完成的功能

**已完成（同一套对话流程覆盖三个场景）：**

- **查询资料。** 模型通过 `list_invoices`、`list_bank_transactions`、`search_rules` 等工具查询当前会话中的企业与会计期间。发票总额、银行收入、银行支出由 Java 在 PostgreSQL 中以整数分汇总，再由程序按证据渲染为两位小数，模型不得在回复里自行填写未经证据支持的金额。查询成功且没有记录时，合计为 0.00 元；发票存在未知金额时，程序拒绝宣称合计完整。工具隐含当前企业与月份，模型不能传入企业或身份参数。
- **补充并保存。** 只允许修改发票的 `purpose`（用途）和 `note`（备注）。流程为：模型调用 `propose` / `create_proposal` 生成建议 → 工作台展示建议卡 → 用户点击「确认保存」→ Java 在事务内锁定发票、复核权限、提案版本和适用规则 → 写入后回查 → 追加审计。确认必须携带 `confirmed=true` 和 `Idempotency-Key`；重复确认返回同一回执。查看者角色不能写入。
- **多轮检查。** 每个账号在每个租户、每家企业最多一个未完成任务（数据库部分唯一索引保证）。任务可追问、更正目标票号或问题、取消，刷新页面后可通过 active 接口恢复；跨会话的建议卡须点击「恢复当前任务」后再确认。保存结论不能凭模型口头判断，须查询 `get_operation` 并引用本轮证据。
- **记忆、规则、运行记录与工作台。** 见第 3、4、7 节。产品由 Next.js 工作台、Nginx HTTPS 网关、Spring Boot、PostgreSQL（含 pgvector）、Redis、Celery、SeaweedFS、FastAPI + LangGraph Agent 组成。

**未完成或不能在本文宣称已验收的部分：**

- 官方 v1.1.0 数据已导入主工作台（Compose 项目 `product`，`https://localhost:3443/`）和隔离实例 `tax-product-p8`（`https://localhost:13451/`）的独立租户 `contest`（40 张发票、48 条流水、R001—R004 及 `u001`/`u002`）。alpha/beta 合成种子未改动。若对 P8 实例从初始 dump 恢复数据库，该实例上的 contest 数据会消失，须重新导入。步骤见 `product/数据导入说明.md`。
- 程序自动收尾（内部称 R5）未实现：模型未给出完整 `answer_items` 时，程序不会代为完成查询答案。
- 团队自写用例 B01—B35 尚未在 v1.1.0 数据上全量复验。此前真实模型三轮重测覆盖的是合成数据上的 B24、B34 主流程及一组 P6 持久化检查。导入后核对了金额回读、权限、规则版本、乙企业门槛下的缺用途清单，以及一次甲企业 2026-09 查询对话。详见 `product/docs/已知限制.md`。
- 发票表只有会计期间（月份），没有按日的开票日期列。
- 不执行真实记账、付款或税务申报，也不做发票图像识别。

## 2. 模型与程序的分工

模型负责理解用户需求，并在每轮最多六次决策中选择 `tool`、`ask`、`answer` 或 `propose`。它决定是否追问、调用哪一个工具、是否生成补全建议，以及如何组织说明。系统提示要求：确认保存由用户点击，模型不可自行确认或声称已经保存；偏好只能影响表达与默认值，不能改变权限、证据规则或确认流程。

程序负责确定性的计算、校验和落库：

- **计算。** 金额在库中存整数分，接口以十进制整数字符串传递；回答中的发票合计、银行收入和银行支出由 `guards.render` 根据本轮成功工具证据渲染。
- **权限。** Java 从 HttpOnly 会话 Cookie 解析账号与租户，再按企业授权表检查角色。`viewer` 不能执行写入（建议、确认、导入等）；无授权的企业直接不可见。会话范围由 Java 签发的短期调用令牌绑定，模型无法通过工具参数改写企业、月份或身份。
- **字段白名单。** `Invoices.validateChanges` 只接受 `purpose` 和 `note`，且必须是非空、不超过 500 字的文本。金额、日期、销售方、项目名称和全部银行记录不可修改。Agent 侧对提案的 `changes` 还要求值必须出现在用户原文中，不得代为编造用途。
- **确认与持久化。** 只有用户明确确认后才写入；写入后回查，不匹配则失败。失败返回原因，不把「建议已生成」或历史回执说成「本轮已经保存」。
- **守卫。** 程序拦截无证据的金额、未确认票号的提案、以及「本轮没有真实提案事件却声称已生成/已保存」的声明。

关于关键词匹配：参赛说明要求不能用关键词匹配或固定场景分支代替模型理解。本产品没有按场景写死查询或保存脚本。程序里确有两处文本规则，但它们只做校验和提示，不代替模型决策：`required_by_text` 会根据用户表述预登记需求种类（如发票合计、银行收支、规则），模型仍可在首次决策中补充遗漏的合法需求，此后清单由程序固定；`proposal_claim` 等正则只用于阻止不实的完成声明。最终是否查询、追问还是提案，仍由模型输出动作决定；没有本轮成功工具证据时，程序不会宣布业务成功。

## 3. 记忆管理

任务、消息、轨迹、偏好和操作均由 Java 写入 PostgreSQL，Agent 不直连数据库，每轮通过 `context` 工具重新领取上下文。

- **会话内。** Redis 保存登录会话（约 1 小时）。对话过程中保留当前企业、月份、任务状态、追问、待确认建议和未核实操作。
- **跨会话。** 刷新页面会恢复登录与未结束任务。注销后再登录，同一账号在同一企业的偏好仍然有效；未结束任务仍受「每企业一个」约束。跨会话看到的建议卡必须先恢复任务、核对原值快照后再确认，不会把已经变化的当前记录冒充提案原值。
- **偏好。** 用户可对本人的用户消息点击「记为偏好」，支持更正、删除和查看版本审计。`user_wide` 为真时 `enterprise_id` 为空，可在该账号同租户下使用；否则绑定当前企业。更正或删除会写入失效记录，旧来源及同轮助手回声不再进入后续上下文。
- **未完成事项。** 上下文包含任务对象、待办问题、待确认提案指针，以及当前账号在该企业、该期间最近五条操作摘要（含真实 `proposal_id`）。摘要只用于定位，保存事实仍须本轮 `get_operation` 证据。
- **隔离。** 记忆与任务均按账号、租户和企业授权过滤，不能读取其他用户或其他企业的记录。

## 4. 知识库与规则管理

规则表 `invoice_rule` 保存编号、版本、来源、条款、正文、必填字段、生效月份和状态（`draft` / `published` / `retired`）。管理员可创建草稿、发布和退役；版本内容写入后固定，修改需发布新版本。生效月份包含当月，失效月份从该月起排除。

实时检索和发票核验只使用 `published` 且覆盖当前会计期间的规则，退役版本不会作为当前业务依据，但「规则版本与检索」列表仍可查看历史版本，已保存的审计回执保留原引用。检索先由 Java 限定候选集，再按字面命中和 pgvector 余弦相似度排序（384 维，FastEmbed 多语言 MiniLM）。回答中的规则由程序渲染为「来源 · 版本 · 条款」加正文。

适用规则缺失或同一条款出现冲突版本时，程序登记人工复核，不继续保存。用户确认时会再次检查适用规则，若规则已变化则退回重新核验。

**官方规则版本选择（租户 `contest`，已在主工作台和 `tax-product-p8` 导入并接口核对）：**

- R001 1.0 与 R004 1.0：两家企业都有，`required_fields` 为空，属于说明类规则。可以被检索，但不参与用途核验选规。`Rules.selection` 只在必填字段非空的规则中选择；没有这一过滤时，说明类规则会把选规变成 `rule_conflict`。
- R002 1.0：仅甲企业 C001，期间为 2026-08 至 2026-09，状态 `retired`（已停用）。2026-09 的规则检索结果不包含该版本。规则原文含 1000 元门槛，导入时写入 `min_amount_cents`，但已停用，不参与选规。
- R002 2.0：甲企业 C001，从 2026-09 起生效，状态 `published`。9 月用途核验依据此版：每张发票都必须填写用途，不设金额门槛。
- R003 1.0：乙企业 C002，从 2026-08 起生效，状态 `published`。Flyway V9 为 `invoice_rule` 增加可空列 `min_amount_cents`。`Rules.requiredFor` 只对 `amount_cents >= min_amount_cents` 的发票要求必填字段，等于 1000.00 元也在范围内（100000 分）。列为空时与原来一样，所有发票都要求。金额未知时按仍须填写处理。因此乙企业 2026-09 缺用途为 F002（1000.00）、F005（1000.01）、F006（1280.50）；低于门槛的 F004（999.99）等不再被标出。2026-08 缺用途为 F016。甲企业 2026-09 仍为 F002、F003、F004、F006、F009。

实测：C001 发票按 R002:2.0 核验，C002 发票按 R003:1.0 核验，状态均为 ready；2026-09 检索可见 R002 2.0、R001 和 R004，看不到已停用的 R002 1.0。「规则版本与检索」列表仍可查看历史版本。alpha/beta 默认种子规则仍是 `product-invoice-completeness` 1 版，与 `contest` 租户分开。

## 5. 模型输入与上下文预算

每轮输入由程序组装，主要包括：系统约束和工具定义、当前企业与月份、本轮用户消息、任务状态、最近操作、未完成提案、本轮工具证据、校验反馈、已登记需求、最近至多八条历史消息，以及有效偏好。需要当前业务数据时必须重新查询，不能只用历史回复中的数字。

预算由环境变量 `PRODUCT_CONTEXT_BUDGET` 控制，单位是 UTF-8 字节，限制在 4096 至 48000。代码未填写时缺省 12000，但官方月度查询（约 10 张发票）会超出该值；推荐填写 24000，主工作台已按此核对通过。超预算时先裁历史消息，再裁偏好，并写入轨迹中的 trimming 记录；若企业、月份、本轮消息等必要内容仍超限，则返回 `context_budget_exceeded`，待办保留。轨迹会记录实际上下文大小和预算，供过程面板展示。密钥不会进入对话状态。

## 6. 数据操作

标准路径是「提案 → 确认 → 保存 → 再查询」：

1. 模型在票号已唯一确认、修改值来自用户原文的前提下调用提案工具。
2. Java 再次校验写权限、字段白名单和适用规则，生成建议及规则引用，工作台展示票号、原值、新值和条款。
3. 用户点击「确认保存」。服务端绑定建议编号与幂等键，锁定发票，重验会话、权限、版本和规则后写入，并以回查结果为准。
4. 用户或模型再次查询该发票，核对应已变更的用途或备注。审计记录改前、改后、经办账号、时间和规则版本。

发票 `revision` 初始为 1，每成功确认一次加 1。失败、权限不足或字段不在白名单时说明原因，不误报成功，也不凭猜测重复修改。

## 7. 运行记录

对话工作台右侧「过程与依据」按轮次展示需求清单、模型决策步骤、工具名称与耗时、工具结果、程序拦截，以及上下文信息（实际字节、预算、使用的偏好条数）。「查看完整轨迹」可展开已脱敏的模型输入和决策，缺省折叠。答案引用了本轮有效证据时，证据卡显示「已核实」。

上述过程经 SSE 事件送达（含 `decision`、`requirements`、`tool_call`、`tool_result`、`proposal`、`answer`、`error`、`done` 及心跳），并由 Java 写入 `agent_trace`。脱敏会替换环境中的口令、Token、API Key 以及会话 Cookie，不记录模型密钥。

## 8. 一个设计选择：提案声明守卫与分动作 Schema

真实模型联调中曾出现：助手文本声称「已按用户信息生成建议」，但本轮没有网关 `proposal` 事件，任务实际停在待补充输入。若只看自然语言，评委或用户可能以为已经可确认保存。

因此程序做了两层约束，而不是改用关键词去「猜」用户想查询还是想保存：

- **提案声明必须对照本轮真实事件。** 结构化字段 `claims_proposal` 以及「已生成 / 已提交 / 已完成修改或保存」一类写操作措辞，都要与本轮带有 `proposal_id` 和 `operation_id` 的提案事件交叉校验。历史保存回执只能证明历史保存，不能证明本轮新提案。拦截后反馈「本轮没有生成提案。要修改就调用 propose 工具，否则如实说明尚未生成。」正则经过收紧，单独说「已完成本月汇总」不会被当成提案声明。
- **按动作种类拆分 Schema，工具枚举不含 `ask`。** `ask` 是独立的 `kind`，不能伪装成工具名。`propose` 的 `changes` 只允许 `purpose` 和 `note`。需求由程序登记后，Schema 不再提供改写入口，避免模型在后续步骤偷偷更换需求。

这样，理解需求和选择下一步仍是模型的工作；程序只禁止在没有真实业务事件时宣布「已经做完」。该选择针对的是不实完成声明，而不是用固定话术替换模型理解。

## 9. 数据导入

官方材料包由 `product/import_contest_data.py` 导入独立租户 `contest`，不覆盖 alpha/beta 合成数据。登录名为小写 `u001`（C001 甲企业、C002 乙企业均为 editor，可查看并修改）和 `u002`（仅 C001 的 viewer；读取 C002 返回 404，对 C001 提交修改返回 403）。密码变量名为 `PRODUCT_U001_PASSWORD`、`PRODUCT_U002_PASSWORD`，写在该实例的 `product/.env`；缺少时脚本会生成并追加，不会打印。

主工作台（Compose 项目 `product`，`https://localhost:3443/`）和隔离实例 `tax-product-p8`（`https://localhost:13451/`）均已导入并核对，Flyway 须升到 V9。在对应实例的源码目录执行（须先重建带 V9 和选规改动的 business 镜像）。主工作台示例：

```powershell
$env:COMPOSE_PROJECT_NAME = 'product'
docker compose -f product/compose.yaml -f product/compose.https.yaml up -d --build --remove-orphans --wait
python product/import_contest_data.py --project product --allow-main --xlsx "<材料包路径>\02_示例数据.xlsx"
```

隔离实例不要加 `--allow-main`，改用项目名 `tax-product-p8` 和覆盖文件 `compose.external-acceptance.yaml`，入口为 13451，详见 `product/数据导入说明.md`。脚本可重复运行，只补缺失行，不会覆盖已经改过的用途和备注；重跑会补上规则的 `min_amount_cents`。项目名不以 `tax-product-p8` 开头时，写入主工作台必须显式加 `--allow-main`。从 `PRODUCT_P8_INITIAL_DUMP` 恢复 P8 数据库后，该实例的 contest 数据会消失，需要重新导入。查询与保存以数据库中的当前数据为准，不要把原始 Excel 当作已保存结果。
