# v1.1.0 赛题数据导入说明（R6 数据部分）

把官方材料包 `02_示例数据.xlsx` 和 `03_业务规则.docx` 的内容导入产品版，供演示和 B 用例复验使用。

## 导入内容

- 独立租户 `contest`，不改动 alpha/beta 合成夹具，原有 verify_* 脚本不受影响。
- 企业：C001 甲企业（比赛模拟）、C002 乙企业（比赛模拟）。
- 账号与权限：
  - `u001`：C001、C002 都是 editor，可查看并修改。
  - `u002`：只有 C001 的 viewer 权限，仅查看；看不到 C002。
  - 密码保存在本副本 `product/.env` 的 `PRODUCT_U001_PASSWORD`、`PRODUCT_U002_PASSWORD` 中。缺少时脚本会生成并追加，不会打印出来。
- 发票：40 张。会计期间取开票日期所在月份；空用途、空备注保存为 NULL。
- 银行流水：48 条。导入时只在同一个事务里临时停用只读触发器，提交前重新启用；应用路径仍然只读。
- 规则：
  - R001 1.0 和 R004 1.0：两家企业都有，属于说明类规则，`required_fields=[]`。可以检索，但不参与用途核验选规。
  - R002 1.0：C001，2026-08 至 2026-09，状态为 retired，即已停用。
  - R002 2.0：C001，从 2026-09 起生效，状态为 published。
  - R003 1.0：C002，从 2026-08 起生效，状态为 published。
- 配套 Java 改动：`Rules.selection` 只在 `required_fields` 非空的规则中选规。没有这个改动时，说明类规则会让选规变成 `rule_conflict`。新增 `RulesSelectionTest` 覆盖这一点。

## 运行

在隔离实例的源码副本根目录执行（不要指向 3443 主工作台）：

```powershell
$env:COMPOSE_PROJECT_NAME = 'tax-product-p8'
# 先重建 business 镜像，带上 Rules.selection 改动
docker compose -f product/compose.yaml -f product/compose.https.yaml -f product/compose.external-acceptance.yaml build business
docker compose -f product/compose.yaml -f product/compose.https.yaml -f product/compose.external-acceptance.yaml up -d --no-deps --wait business
python product/import_contest_data.py --project tax-product-p8 --xlsx "<材料包路径>\02_示例数据.xlsx"
# 只核对、不写入：
python product/import_contest_data.py --project tax-product-p8 --xlsx "<...>\02_示例数据.xlsx" --check-only
# 接口核对（权限、规则版本）；加 --chat 会额外发起一次真实模型对话
$env:PRODUCT_TEST_BASE = 'https://localhost:13451'
$env:SSL_CERT_FILE = (Resolve-Path product/tls/local/ca.crt).Path
python product/verify_contest.py --chat
# 离线单测（设置 CONTEST_XLSX 后会额外比对官方工作簿）
python -m unittest product/test_import_contest_data.py -v
```

- 项目名不以 `tax-product-p8` 开头时，脚本拒绝写入。写主工作台必须显式加 `--allow-main`，并且要先重建主工作台的 business 镜像。
- 脚本可重复运行：只补缺失行（ON CONFLICT DO NOTHING），不会覆盖已经修改过的用途和备注。
- 从 `PRODUCT_P8_INITIAL_DUMP` 恢复数据库后，contest 数据会消失，需要重新运行导入。

## 金额门槛（V9，2026-11-12 补做）

- Flyway `V9__rule_amount_threshold.sql` 给 `invoice_rule` 增加可空列 `min_amount_cents`。
  - 规则的 `required_fields` 只对 `amount_cents >= min_amount_cents` 的发票生效，等于门槛也算在内。
  - 列为空时与原来一样，所有发票都要求。
  - 发票金额未知时按要求处理，偏保守。
- 门槛依据 03_业务规则.docx 中 R003 1.0 原文：「单张发票金额大于或等于 1000.00 元时必须填写用途，等于 1000 元也在范围内」，所以取 100000 分（≥）。
  - 已停用的 R002 1.0 也按原文写入 100000，只作版本留档，不参与选规。
  - R002 2.0 没有门槛，甲企业不受影响。
- Java 端：`Rules.requiredFor(rule, amount)` 先按门槛算出这张发票的必填字段，再交给 Agent 的 invoice-review。check_purpose、生成提案时的核验，以及 review 接口都走这条路径。Agent 镜像不需要改。
- 导入脚本对规则行使用 `ON CONFLICT ... DO UPDATE SET min_amount_cents`。V9 之前已经导入的库，重跑一次脚本就能补上门槛；规则的其他列不改。
- 必须先重建 business（Flyway 升到 V9），再运行导入脚本。
